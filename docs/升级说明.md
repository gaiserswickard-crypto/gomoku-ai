# v2：根据平台败局完成的改进

本页记录 v2 历史版本，源码和可执行文件已备份到 `versions/v2/`。当前 `main.cpp` 为 v3 棋库版，见 `docs/棋库版说明.md`。

更新日期：2026-11-03。提交文件仍为项目根目录的 `main.cpp`，单文件 C++17。正式本地程序 `build/gomoku.exe` 已重新编译。原版保存在 `versions/v1/`，本次没有代替用户上传平台或发起比赛。

## 从实际棋谱确认的问题

已从用户打开的提交详情页，读取 lincr、乌云典当、Bilibili 链接昵称三场比赛的六局完整日志。共五负一和，全部正常结束。颜色以日志中的 brain `1` 配置为准。

逐手检查没有发现漏走立即胜点、漏堵唯一胜点。五场败局最后一次己方回合都已面对两个成五点，真正问题发生在更早的组合进攻阶段。具体线路、证据和不确定性见 `results/platform/analysis.md`。

一个可验证的改进点是 Bilibili 对手那局白方第 18 手：旧走法 `(2,7)` 允许对方连续冲四获胜。独立枚举全部 123 个合法点，122 个有明确连续冲四反驳，只有 `(6,3)` 未被该检查证明输。新版选 `(6,3)`；这不等于已经证明能赢或守和。此局面已加入回归测试。

乌云典当白局第 8 手，新版在本机给定 1140 毫秒预算时由 `(9,3)` 改选 `(6,3)`。该局面的胜负仍含更深的活三及安静着法，不能仅凭换点认定整局已被修复。

## 最终保留的变化

1. **超时选点修正。** 深一层已完整搜索的候选可替换旧最佳点，避免因后续候选超时而丢弃已经得到的反驳。
2. **完整的双胜点防守集合。** 既检查堵攻击点，也检查堵连线另一端，并保留己方冲四反击。叶子仅对确实无法防守的双威胁证明败，不无限扩展活三分支。
3. **候选点的对手 VCF 检查。** 根节点用有限时间排查已证连续冲四败点；未知结果不作为败点剔除，所有候选均被反驳时仍保留合法走法。
4. **减少无效计算。** 使用棋形编码直接检查防守、增量胜点位图、当前棋盘的严格对称去重，使更多时间用于有效搜索。

曾尝试扩大叶子处的防守搜索，但整局对比出现退步，因此未将该版本作为最终方案。实验结果保留在 `results/platform/`；不要把不同实验版的结果混作当前源码胜率。

## 验证方式与结果范围

最终源码的五个 C++ 测试程序全部通过：覆盖原有 11 组战术、600 个随机棋盘/1200 次选点、1290 个成五后的棋盘、48 个防守集合与独立穷举的对照、实际平台败局和冲四反击，以及初始盘、非对称盘和 64 个构造棋盘的对称剪枝。位图也在 `verifyState()` 中逐点与重算结果比较。重新编译的正式程序通过全部 9 项协议测试。

完整对战由 `tools/arena.py` 重新交替执黑、执白运行对手进程。对局中双方每一步都会重新计算；改变自己的落子后没有假设真实同学仍会照旧棋谱应答。正式源码的测试结果与 SHA-256 记录在 `results/platform/v2_validation.json`。
