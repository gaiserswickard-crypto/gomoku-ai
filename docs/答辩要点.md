# 五子棋程序答辩要点

下面是围绕当前实现的复习提纲。理解每个机制解决了什么问题，比只记算法名称更有用。

## 1. 棋盘和协议

棋盘是一维 `std::array<int, 144>`，坐标映射为 `pos = row * 12 + column`。0 表示空，1 表示黑，2 表示白。用一维数组可以把位置、哈希键、评分和历史表都用同一个整数下标访问。

`START` 设置自己的颜色并恢复题目给定的中央四子。`PLACE` 只接收对手棋子，不输出响应；`TURN` 搜索并记录己方棋子后输出坐标。每次输出立即刷新。`END` 或 EOF 结束进程。真正对局中的棋盘由这些指令逐步积累，不会每步重新启动。

判胜从最新棋子沿四个方向向两侧计数，至少五颗即胜。这是无禁手规则，所以六连也能赢。

## 2. 为什么采用搜索

单纯挑当前棋形得分最高的点，只看得见局部收益，可能忽视对手下一手的必杀。搜索交替模拟双方落子，假设对手也选择有利于自己的应对，再决定本手走法。

Negamax 利用双方零和的关系，把“对手得到的分数”取负转成自己的分数。Alpha-Beta 用已有的上下界跳过无法改善选择的分支；在同一棵完整搜索树和同样的叶子评估下，它保留 Minimax 的结果。本程序另外用了候选截断、LMR 和战术延伸，因此实际搜索树经过了选择，不能宣称穷举求出了全局最优解。

PVS 先完整搜索排序最好的候选，再用很窄的窗口检查其他候选是否值得认真搜索。若后来的候选超过当前最好值，重搜确认其真实价值。着法排序好时可以减少大量工作。

## 3. 怎样表示棋形

假设在一个空点落己方棋子，将它视为中心。每条方向取左四格、右四格，每格分为空、己方、阻挡三类，共 `3^8 = 6561` 个编码。边界与对手棋子一样，都会阻断己方连线。

查表内容是启动时由窗口枚举计算出来的，包含是否成五、能成五的不同空点数、能否继续形成活三等特征。四个方向合并得到这个落点的攻击潜力；也计算对手在同一位置落子时的潜力，用于考虑防守。

“两个成五点”必须是两个不同的空点。两个五格窗口可能都缺同一格，这仍然只需对手下一手堵一次，因此程序按空点去重。

棋形评分只是启发。双三或四三会给较大加分，但其胜负仍可能受到对手先手、边界和其他方向威胁影响，不能只看分数宣布必胜。

## 4. 增量更新为什么更快

一个落点只会影响经过它的四条线，其他线的编码和评分不变。因此 `setStone()` 和 `undoStone()` 只更新预先记录的受影响位置。周围两格内的候选计数也增量维护。

撤销必须与落子严格对应：棋盘、棋子数、棋形编码、候选计数和哈希都要恢复。如果漏撤销一个字段，搜索会在错误棋盘上继续。`verifyState()` 用完整重算检查这些增量数据；测试还比较搜索前后棋盘是否一致。

## 5. 连续冲四与叶子延伸

冲四制造一个下一手就能成五的点，对方通常必须立即堵住。VCF 搜索正是利用这个强制应手，把一段“冲四、堵住、再冲四”的长序列变成较窄的搜索。

每步仍需检查对手能否立即成五，否则自己的冲四不能迫使已经可以获胜的对手防守。形成两个不同的成五点且对方不能立即取胜时，对方一手堵不全，可以证明这段杀棋成立。

VCF 找不到并不表示局面没有胜法，可能存在需要活三、安静铺垫或更长计算的胜法。本实现还设置深度和时间上限；上限触发只能得到“未知”。

普通搜索到深度边界时也处理直接胜负、必堵与冲四，降低地平线效应。例如搜索正好停在对手冲四之前，静态评分可能觉得局面还不错，而继续看强制应手才能发现真正后果。

## 6. 置换表怎样保证信息含义正确

不同落子顺序可能到达同一局面。Zobrist 哈希给每个“位置、颜色”一个固定的 64 位随机数，落子和撤销都用异或更新。查询键还包含轮到哪一方行动，相同棋盘但不同走子方不能混用。

表项不仅保存一个分数，还保存搜索深度和类型。精确值可直接用；下界表示真实分数至少这么高，上界表示至多这么高，只有满足当前 Alpha-Beta 窗口条件时才能剪枝。搜索中途超时的结果不会写成一个完成的搜索结论。

杀棋分数含“距离终局还有多少手”，优先选择更快获胜、尽量延缓失败。存入和读出置换表时调整层数，避免同一局面从不同深度到达时误用距离。

## 7. 为什么既要限制单步，也要限制整局

每步不超过 2 秒仍可能在长局里累计超过 90 秒。当前实现用单调时钟统计己方计算时间，以 80 秒为整局目标，除以剩余可能走子的次数；再与默认 1.4 秒单步上限取较小值。

迭代加深先完成浅层搜索，再尝试深层。v2 在新一层先搜索上一层最佳点；超时时撤销未完成的试走，并保留当前层已经完整搜索的最佳候选。这样可以避免明知旧最佳点在更深处输棋，却仍因本层未全部完成而选回旧点。若本层还没有完整候选，才使用上一层结果。直接胜负和必堵还可以很快返回。

v2 的防守判定区分“有下一手双胜点威胁”与“无论怎样都防不住”：对手的两个攻击点可能通过堵同一条线的另一端一起化解；己方冲四也可能迫使对手先防守。只有把这些应手全部排除，才可证明局面必败。叶子搜索不盲目扩展所有活三防守，防止分支过多反而降低有效深度。

搜索深度是动态结果，不是“每一步必定看固定多少层”。局面复杂程度、强制应手数量和 CPU 速度都会影响实际完成深度。

## 8. 怎样说明测试结论

战术测试验证明确的局面性质，如唯一胜点、唯一堵点、长连、满盘与状态回滚；完整对战验证连续协议交互、每步合法性、用时和最终结果。两者互补。

v1 初次与参考程序换色两局均胜，v2 后来的实测为一胜一负；v3 棋库版对 v2 和参考程序均为执黑胜、执白负。不同版本的结果须分别报告，不能合并成当前版本胜率，也不能称为全班胜率 100%。

可以现场准备一个小例子：黑棋已有同一行四颗连续棋子，另一端被白棋堵住。解释为什么程序必须选唯一成五点；随后交换颜色，说明同一位置为什么变成必须防守点。再用一个跳四例子说明“连子长度”不足以识别全部威胁，为什么需要按五格窗口检查空位。

## 9. 棋库为什么能放进单文件

v3 从公开 RenLib 棋谱中提取课程固定四子对应的花月分支。先剪掉重复落子及越界线路，再用前序树保存落点和子节点数；多数节点只需两个字节，最后用 Base85 转成安全的源码字符串。完整源码 858,578 字节，无需 LZMA 解码器，运行时也不读取外部棋谱。

查找使用完整棋盘逐格匹配，既比较位置也比较颜色和棋子总数，因此不会因为少量局部相似或哈希碰撞误命中。对称只采用保留整个 12×12 棋盘边界和双方颜色的变换。

棋库是建议，不是必胜证明。公开谱既有未覆盖的白方应手，也有未证明的叶子，甚至有少数漏堵建议。程序先取立即胜点、处理必堵，再检查棋库推荐的双威胁防守和对手 VCF；未命中或已证危险的推荐交还搜索。必须区分“在谱内查到一步”“有限时间未发现反驳”和“对所有合法应手都证明必胜”。数据来源及实际效果应如实说明。
