# 五子棋对战程序

这是面向 2026 年课程比赛的单文件 C++17 程序。提交文件是 `main.cpp`；程序通过标准输入、标准输出与评测平台交互。本地还提供对战器、战术测试及算法说明。

当前源码为 **v3 棋库版**，在 v2 搜索引擎上嵌入花月开局的相关走法树，执黑时优先查询，未覆盖的局面及执白继续搜索。完整单文件为 **858,578 字节**，低于 1 MiB 限制；运行时不读外部文件。说明和实测见 `docs/棋库版说明.md`。这份棋谱没有经过完整必胜证明，不能承诺执黑必胜。

原版与 v2 源码、可执行文件分别保留在 `versions/v1/`、`versions/v2/`。历史败局改进见 `docs/升级说明.md`，逐手复盘见 `results/platform/analysis.md`。尚未代为向学校平台提交新版。

## 先运行起来

在本目录打开终端。Windows 可以运行：

```powershell
.\build.bat
```

生成的程序是 `build\gomoku.exe`。脚本优先使用 PATH 中的 `g++`，其次使用 MSVC；当前电脑已配置的 Visual Studio 路径也包含在脚本中。换电脑后，可在 Visual Studio 的“x64 Native Tools Command Prompt”里运行脚本。

Linux 或安装了 G++ 的环境：

```bash
g++ -O2 -std=c++17 -Wall -Wextra -pedantic main.cpp -o gomoku
```

平台选择 **G++ / C++17**，提交 `main.cpp` 的内容即可。其他文件用于本地学习和测试，无需提交。Windows 的 `.exe` 不能直接放到 Linux 平台运行。

可手动输入以下指令确认程序工作；程序会先输出 `OK`，再输出一对落子坐标：

```text
START 1
TURN
END 0
```

这是机器对战程序，没有图形棋盘。每局保持同一个进程，程序会记住双方已落的棋子。

## 已适配的比赛规则

| 项目 | 处理方式 |
| --- | --- |
| 棋盘 | 12×12，坐标是行、列，均为 0～11 |
| 初始棋子 | 黑方 `(5,6)`、`(6,5)`；白方 `(5,5)`、`(6,6)` |
| 行棋顺序 | 初始四子放好后，黑方先行 |
| 胜利 | 横、竖或两条斜线连续至少五子；没有禁手，长连也算赢 |
| 每步限制 | 平台上限 2 秒，程序默认搜索上限 1.4 秒，并按整局余量进一步缩短 |
| 整局限制 | 平台上限 90 秒；程序按 80 秒目标分配剩余回合预算 |
| 启动限制 | `START` 需要在 1 秒内回复 `OK` |
| 内存限制 | 平台上限 350 MB；程序主要固定开销是约 24 MiB 的置换表，具体大小由编译器布局决定 |
| 运行方式 | 单线程、标准 C++17，不依赖运行时文件、网络或额外库 |

特别注意：中央四颗棋子已经在 `reset()` 中初始化，来源是题目 PDF 最后一页的开局图，不能把比赛当成空棋盘开局。

协议处理如下：

| 输入 | 行为 | 标准输出 |
| --- | --- | --- |
| `START 1` / `START 2` | 清空上一局状态、恢复初始四子、设置己方颜色 | `OK` |
| `PLACE r c` | 记录对方落子 | 无 |
| `TURN` | 搜索、记录己方落子 | `r c` |
| `END result` | 结束进程 | 无 |
| 输入结束 EOF | 正常退出 | 无 |

每次应答都立即刷新输出缓冲区，避免评测平台等待不到响应。非法 `PLACE` 不会写出棋盘范围或覆盖已有棋子。

## 搜索是怎样工作的

`chooseMove()` 先做直接战术判断：自己能一步成五就取胜；对手有一步成五点就优先堵住；若自己一手能制造两个不同的成五点，则走该点。对手已经有两个不同成五点且自己无法立即取胜时，局面已经无法靠一手全部封住，程序仍返回一个合法防守点。

v3 在这些直接战术之后查询黑方棋库。查询逐格核对完整局面和轮次，支持保持颜色的全盘对称以及不同落子顺序。棋谱推荐还须通过双威胁防守检查和短时对手连续冲四反驳检查；没有被反驳只表示未知，不表示必胜。失配、查询超时或推荐被全部排除时，继续下面的普通搜索。

之后执行连续冲四搜索（VCF）。冲四会迫使对方立即防守，因此可以沿着强制应手继续搜索，直到形成双重威胁或直接成五。实现同时检查对方能否抢先成五。没有找到、深度耗尽或时间耗尽，均只表示“没有证明存在这条杀棋”，不会当成必败结论。VCF 使用本步预算的一部分，普通搜索仍有时间可用。

普通搜索使用 Negamax 形式的 Alpha-Beta，并结合 PVS。第一个候选完整搜索，后续候选先用窄窗口检查能否超过当前最好结果；确有可能改进时，再扩大窗口重搜。搜索深度从 1 开始逐层增加。更深一层首先检查上一层的最佳点；如果随后计时中断，保留本层已经完整搜索过的最佳候选，避免退回本层已经否定的旧落点。如果本层尚无完整结果，则沿用上一层结果。

落到普通搜索的深度边界后，程序还会延伸处理直接成五、必须防守和冲四，减少“刚好在关键连招中间停止计算”的问题。搜索中的强制堵点也会获得深度延伸。

v2 额外检查对手下一手形成双胜点的威胁。普通搜索保留能消除所有此类威胁的防守，以及己方冲四反击；叶子处只在确认没有任何防守或反击时判败，不无限扩展活三分支。根节点还会短暂检查候选点是否让对手获得连续冲四胜法：只排除已被证明输、且存在其他未被反驳候选的点。证明超时始终按未知处理。

### 棋形查表与增量更新

对每个待选空点，假设在这里落一颗己方棋子，分别检查横、竖和两条斜线。每条线向两端各取四格，共八个邻格；空格、己方、对方或边界分别编码为 0、1、2，因此只有 `3^8 = 6561` 种情况。

`buildPatterns()` 在启动时建立查找表。它枚举包含中心点的五格窗口，识别成五、不同的成五补点、活三等特征。多个窗口指向同一个补点时只计一次，所以一个跳四不会仅因重复窗口而被误认成两个独立威胁。四个方向的特征在 `combine()` 中合并，四三、双三等组合获得较高启发分。

搜索每落一子或撤销一子，只更新受影响的四条线及附近候选计数，无需重新扫描整个棋盘评估所有棋形。落子与撤销还会同步维护 Zobrist 哈希。

直接胜点和双胜点用增量位图维护，减少反复扫描。检查防守能否破坏某个双胜点时，直接修改该方向的假想编码并查表，不实际落子。开局中若当前整盘棋存在保持双方颜色的镜像或旋转对称，根节点只搜索每组等价着法的一个代表；没有硬编码某个对手的开局答案。

### 怎样控制搜索量

- 普通候选主要来自已有棋子周围两格范围。先按己方攻击价值、对方威胁价值、历史表现等排序。
- 普通候选数量受限，但已识别出的冲四、活三等战术候选保留。根节点最多保留 28 个普通候选，内部节点按深度保留 14 或 20 个普通候选，另加战术候选。
- 排位较后的普通候选先减小搜索深度（LMR）；若结果足以改善当前选择，再按完整深度复核。
- 置换表按“棋盘哈希 + 轮到谁走”存储深度、最佳着法以及精确值、上界或下界，减少重复搜索。杀棋分数做了层数归一化，以便不同路径到达同一局面时复用。
- History 和 Killer 记录曾经有效的着法，帮助下一次更早发现可以剪枝的分支。

这些措施提高了有限时间内的有效搜索深度，也意味着普通搜索是有选择的搜索，并非穷尽所有可能。棋形评分是排序与评估的启发值，不是胜率百分比；尤其四三、双三的高分不能直接等同于已证明必胜。

## 本地验证和对战

战术测试可在 Linux/G++ 下编译运行：

```bash
g++ -O2 -std=c++17 tests/tactics.cpp -o tactics
./tactics
```

在 MSVC 开发者终端中：

```bat
cl /nologo /O2 /EHsc /std:c++17 /utf-8 tests\tactics.cpp /Fe:build\tactics.exe /Fo:build\tactics.obj
build\tactics.exe
```

测试覆盖初始化、直接取胜、必防、跳空成五、棋盘边缘和斜线、长连、满盘、重置、连续冲四，以及随机落子/撤销的增量状态一致性。每次搜索还检查棋盘是否完全恢复，防止把搜索中的试走留在真实局面上。

另有独立规则校验与协议测试。Linux/G++ 环境可直接执行 `make test`；也可以分别运行：

```bash
g++ -O2 -std=c++17 tests/oracle.cpp -o oracle
./oracle
python3 tests/protocol_test.py --engine ./gomoku
```

Windows 上已编译的测试可用 `build\tactics.exe`、`build\oracle.exe` 运行；协议测试命令是 `python tests\protocol_test.py --engine build\gomoku.exe`。随机规则校验不依赖引擎的棋形表，使用独立枚举对照立即胜点、唯一防点和判胜结果。

v2 增加 `tests/defense.cpp`、`tests/platform.cpp` 和 `tests/symmetry.cpp`，覆盖完整防守集合、边线两端封堵、双活三、冲四反击、平台第 866b 局白方第 18 手的已知连续冲四败点，以及保留棋子颜色的对称剪枝。这些回归都已包含在 `tools\test_windows.bat` 和 Linux 的 `make test` 中；Windows 协议测试另行运行。

v3 再增加 `tests/book_runtime.cpp`、`tests/book_engine.cpp`：检查精确命中、错误颜色、额外棋子、换序、对称坐标、损坏数据、未收录应手回退，以及实际棋谱中的错误推荐被立即取胜/必堵覆盖。上述 Windows 脚本和 `make test` 现在均包括全部七个 C++ 测试程序。

本地对战器只依赖 Python 标准库。编译参考程序后，可从本目录执行：


Linux 下将程序路径换成相应的可执行文件，例如 `./gomoku`、`./reference`。参考程序可这样编译：

## 怎样继续提高棋力

优先保存平台败局，定位“漏看一步成五”“连续冲四没看完”“候选点被排除”“普通局面评价不准”等具体原因，再把该局面加入回归测试。这样比同时改很多评分常数更容易判断修改是否有效。

需要调参时，一次只改一个方面，保留旧版本，双方交换黑白对战，再检查用时。候选宽度增加不一定更强：同样的时间里，搜索可能因此变浅。也不建议直接把每步预算拉到 2 秒附近；平台 CPU 速度和调度会变化，还要考虑整局时间限制。

定义 `GOMOKU_DEBUG` 后，程序会向标准错误输出完成深度、评分、节点数和累计计算时间，供本地分析。例如：

```bash
g++ -O2 -std=c++17 -DGOMOKU_DEBUG main.cpp -o gomoku_debug
```

`GOMOKU_MOVE_MS` 可在编译时设定本步搜索上限；整局预算仍可能将它进一步调低。默认值是 1400 毫秒。

## 代码阅读建议

`main.cpp` 内含较大的自动生成棋库字符串。阅读算法可先看不含数据的 `src/engine.cpp`，再看 `tools/book_runtime.inc` 和负责接入的 `tools/build_book.py`。建议顺序：`main()` 的协议处理 → `reset()` 和棋盘表示 → `winsAt()` → `buildPatterns()` / `combine()` → `setStone()` / `undoStone()` → `chooseMove()` → `proveFours()` → `search()` / `quiescence()`。答辩复习可参考 `docs/答辩要点.md`。

修改上述引擎基底、棋库模块或生成器后，用 `python tools/build_book.py --output main.cpp` 重新生成，再运行编译和测试。重新生成会覆盖对 `main.cpp` 的手动修改。原始棋谱保存在 `tmp/book_research/flower_public.lib`，来源及转换记录见 `docs/棋库版说明.md`。

搜索引擎、棋谱解析和查询代码自行实现，花月走法数据来自公开棋谱；来源与转换过程均已记录。往年源码保留在 `reference/`，用于分析和本地对战。题目要求独立完成并能解释算法，提交与答辩时应如实说明所用数据、参考与辅助过程。
